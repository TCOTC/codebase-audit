# 挑战门 — 发现有效性审查

## 目的

AI 审计最大的失败模式不是「没找到问题」，而是**误判方向**。两个方向都会发生：

1. **把不属于缺陷的东西报告为缺陷**（假阳性）：触发原因是**合理化**（rationalization）——先匹配上某个模式，再为结论找理由，而不是先判断再匹配；或「应该这样写」只是审计者的个人意见，没有任何规范、文档或既有约定支撑
2. **把真缺陷判为噪声**（假阴性）：形式上表现为驳回有理，而实际理由是错的。这是更隐蔽也更贵的一类——它不会污染报告，但会把真问题埋掉，且**一旦写进「已知误报」就会长期过滤掉后续同类命中**

挑战门是对每条发现的自我对抗审查。机制参考社区先例 `github/awesome-copilot` 的 `quality-playbook` skill（MIT）中的同名机制，按其两轮结构与三档裁决适配。

## 两轮对抗

每轮使用**全新的 subagent**，确保挑战者对该发现没有立场投入。

### 第一轮：「这看起来像真问题吗？」

提供给 subagent：
- 发现的完整描述（含判据编号与建议）
- 所引用位置的**实际源码**（重新读取，不要相信描述里的代码片段）
- 引用位置上下各 10 行内的全部注释
- 项目文档中相关章节（若有）

提问要点：

> 你在审查一份提交给开源项目的缺陷报告。阅读源码与报告后回答：**这看起来像真问题吗？**
>
> **先运用常识。** 如果你把这段代码和这份报告给一位从未见过它们的资深开发者看，他会说「对，这是个问题」，还是「这显然不是问题」？若答案显然是后者，直接说明并解释。不要用分析绕过常识判断。
>
> 然后考虑：
> - 开发者是否**已知**此行为？（查找注释、TODO、设计决策说明）
> - 这是否是**有意的设计取舍**或**已记录的已知限制**？（其他代码路径是否刻意不同）
> - 「预期行为」是否有**任何权威依据**？还是仅仅是审计者的意见？
> - 这是否属于**开发阶段的占位**？名为 placeholder / example / default 的值不是缺陷。
>
> 最后追问：「一个知道自己在看什么的人类，看完报告里的『业务表现』与『预期表现』两句后，会直接判为值得修吗？」
> 若不能，说明业务影响尚未描述清楚，该发现应退回补充而不是进入报告。

### 第二轮：定向追问

根据第一轮立场生成一个尖锐的反问，用新的 subagent 执行。

**若第一轮判为「真问题」**：让 subagent 扮演维护者反驳。

> 你是本项目的维护者，被质疑的代码是你写的。阅读代码、报告与第一轮的判断。
> 写出「这不是缺陷」的最有力论证：有意设计、已记录限制、部署场景、语言/框架惯用法、以及「预期行为」是否真的在任何权威处被规定过。
> 给出论证后，说明你最终是否仍认为这是真问题。

**若第一轮判为「不是问题」**：让 subagent 挑战该驳回。

> 你是安全/质量研究者，另一位审查者驳回了这条发现。阅读代码、报告与第一轮的驳回理由。
> 写出「这确实是真问题」的最有力论证：驳回未覆盖的边界、下游后果、与其他组件交互时的行为、以及「有意为之」与「正确」是否等同。
> 给出论证后，说明你认为该发现应被确认还是驳回。

## 三档裁决

| 裁决 | 条件 | 后续动作 |
|---|---|---|
| **CONFIRMED** | 两轮均认为成立，或第二轮未能动摇第一轮的确认 | 正常进入报告 |
| **DOWNGRADED** | 问题真实但严重度被夸大 | 调整严重度与影响描述后保留 |
| **REJECTED** | 不成立：已记录的设计选择、开发占位、已知限制、审计者个人意见 | 移除；理由记入「已审查并驳回」附录 |

**REJECTED 不是失败**，它是挑战门正常运作的标志。宁可驳回一条模糊的发现，也不要让报告被噪声淹没。

### 裁决之外还要记两件事

1. **论据是否被纠正**。裁决可能不变而论证被推翻——这是常态，不是驳斥。
   实测：一条发现判 CONFIRMED（真问题），但第二轮指出我用于支撑它的两处论据都是错的（RFC 条款被误引、
   「404 不可表达」不成立，而根包已导出 `NewHTTPError`）。
   **必须把纠正后的论据写回报告**，否则后续读者会用错误论据去理解一个正确的结论，修法也会跑偏。
   报告模板的「挑战门」字段要写成 `CONFIRMED（论据已纠正：<哪一处>）`，不能只写 `CONFIRMED`。
2. **建议的修法方向是否危险**。挑战门审的是发现，但报告里同时给出建议，**建议也会错**。
   实测：一条真缺陷的正确修法需要返回 404，而兄弟路径返回的是普通 error（经上游 `ServeError` 映射为 500）；
   若照抄兄弟路径，会把「成功的幂等重试」变成服务端故障——**比原缺陷更糟**。
   挑战门的第一轮就要把「建议」一起审，尤其当建议形如「照抄另一处实现」时：问清两处的**上游消费方是否相同**。

### 降级理由本身也要过门

**挑战门的第一轮也可能错。** 实测：我曾以「`os.RemoveAll` 对符号链接只删链接本身、不递归进目标」为理由把一条路径越界发现降为「防御纵深不一致」；
该断言只对**叶子**成立——中间组件是软链时 `unlink` 会解析全部前导组件、`RemoveAll` 打开 parentDir 时也没有 `O_NOFOLLOW`，
实际是**递归删除目录外的整棵树**，真缺陷被错误降级。

因此：**凡「降级理由本身是一条技术断言」的，必须再验该断言**，不能只验它是否听起来合理。
常见的这类断言：

- 「浏览器/框架会忽略它」（实测反例：Chromium 确实忽略子资源上的 `Content-Disposition`，但它**不**忽略顶层导航）
- 「CI 跑不到这条」（**不是免报牌**：测试在目标平台上确定失败本身就说明不可移植；跑不到是独立缺陷，见判据 G4）
- 「上游不会这样分派」（必须读上游源码确认，路径形态与存在性常是正交的）
- 「无消费方所以无影响」（需 grep 确认全仓无读取方，而不是没搜到就认定）

**误判为误报的代价是双向的**：真缺陷被写进「已知误报」后，后续每轮都会把它当噪声过滤掉。
实测一例：宿主 MIME 注册表影响内联安全判定的问题先被列入误报，后来才发现是真缺陷（已提 issue 并修复）。
因此对已录入的误报抽查时，不能只看它「说得通」，要看它的**降级理由能否被一次实验或一段源码推翻**。

## 自动触发条件（高误报类别）

以下类别**必须**过挑战门，其余可跳过以节省成本：

| 触发条件 | 误报集中的原因 |
|---|---|
| 安全类发现（凭据泄露、鉴权绕过、注入） | 严重度自动升级，模型倾向于为之辩护 |
| 引用位置 10 行内有设计决策注释 | 注释表明开发者是**有意**这么写的 |
| 「预期行为」缺少规范依据 | 需求是审计者**自己发明**的，而非从项目约定推导 |
| 同一关注点在其他代码路径处理方式不同 | 可能是真不一致，也可能是**有意区分** |
| 发现属于「缺少功能」而非「行为错误」 | 「这个处理器没做 X」往往是功能缺口，而非缺陷 |
| 与本仓库 `AGENTS.md` 明示规则冲突 | 可能审计者未读到项目约定 |
| 发现只给出代码层结论，无业务表现 | 「变量写反」本身不是影响，可能实际行为未被任何路径触及 |
| 「预期表现」的权威依据只引用了审计者的推断 | 预期可能是审计者自己发明的，而非项目约定/既有正确实现 |
| **降级理由是一条技术断言** | 断言可能只对部分输入成立（如只对叶子软链、只对子资源请求），需实验或源码再验 |
| 引用了外部系统/上游库的行为（浏览器、框架、协议） | 行为可能只对部分输入成立，且**部分成立最容易蒙过人**；必须实测或读上游源码取证 |

此清单刻意保守。新增触发条件时，附上理由与一个来自往轮的具体实例。

> 注意：本仓库的同步忽略规则、加密笔记本、快照格式在 `AGENTS.md` 中有明确的**兼容性条款**。审查这类发现时，必须先确认是否与已声明的兼容性策略冲突——**忽略集合的变动会导致其它设备签出时删除文件**，这类「优化」是高风险改动而非缺陷修复。

## 成本

每条触发挑战门的发现约需 2 次 subagent 调用。若触发条目超过 15 条，可先批量跑完第一轮，
但**下列情形必须跑第二轮**，不能为省成本省略：

- 第一轮的**理由是一条技术断言**（而非「这是有意设计」这类事实判断）——断言需要再验，
  而第一轮出错的主要形态就是把断言当成事实（见「降级理由本身也要过门」）
- 发现的**建议形如「照抄 / 对齐另一处实现」**——需确认两处的上游消费方相同
- 安全类，或严重度需要往高估

第二轮的产出往往比第一轮有价值：实测中**纠正错误论据**与**阻止有害修法**都发生在第二轮。

## 与置信度的关系

挑战门结果写入报告的「挑战门」字段。未触发的写「未触发」。
**置信度为「低」的条目必须过挑战门**，否则不得进入报告主列表，只能作为附录观察项。

字段要同时记下**裁决**与**论据是否被纠正**，例如 `CONFIRMED（论据已纠正：RFC 误引）`、
`DOWNGRADED（原判为越界读取，实为 UX 一致性）`。只写一个词会让后续读者重复犯同一个推论错误。
