# 差分审查模式（审一个 diff）

> **触发条件**：用户给了 PR / commit / 分支 / 一组改动文件，要求「看看这次改了什么、有没有问题」。
> 与「审计模式」的区别只有一处——**范围从目录变成 diff**，判据与挑战门完全复用。

## 为什么这个模式值得单列

`evidence.md` 的量化结论：**200 个 bug 提交里 58.5% 只碰 1–2 个文件、中位数 31 行**。
也就是说，真实修复场景绝大多数是**小 diff**，而不是「扫描一整个包」。
只按目录定范围，最常用的场景反而没有对应流程。

## 与其它三种模式的分工

| 模式 | 输入 | 回答的问题 |
|---|---|---|
| 审计 | 目录/包 | 「这段代码里藏着什么问题」 |
| **差分审查** | **diff** | 「**这次改动**引入了什么、漏了什么」 |
| 修复 | 已确认的缺陷 | 「怎么改，改得对不对」 |
| 验证 | 已提 issue | 「之前报的问题处理得怎样」 |

差分审查的独有产出是**「漏改」**：同一处改动在 A 点做了，对称的 B 点没做。
这类问题在按目录扫描时会被当成「B 点本来就长这样」而放过，只有以 diff 为锚才看得到。

## 流程

### 1. 取 diff，先做回归检测（必做，零成本）

```bash
git diff --name-only <base>            # 或 --cached / HEAD~1 / 分支名
python "<skill-dir>/scripts/scan_regression_index.py" --git <仓库> --rev <base>
```

第二步会报出「本次改动命中历轮发现」的文件、当时轮次、issue 与行号，以及高复发文件排行。

**为什么这一步必须最先做**：改动落在历轮已报告过的位置时，回归概率显著高于新代码。
命中不等于回归（行号是当时的位置，会随提交偏移），但它把「该重点看哪几个文件」
从经验判断变成机械排序。**这是唯一能在读代码之前就缩小范围的环节。**

### 2. 按改动性质分类，而不是按文件分类

逐个文件读 diff 效率很低。先给**每个 hunk** 打两个标签，再按标签决定要不要深看：

| 维度 | 取值 | 影响 |
|---|---|---|
| 改动种类 | 新增 / 修改 / **删除** / 重命名 | 删除与重命名最容易漏改调用方 |
| 内容性质 | 逻辑 / 配置 / 契约 / i18n / 文档 / 测试 / 纯格式 | 契约与 i18n 有外部同步义务 |
| 是否对称 | 成对出现 / **单边出现** | 单边即判据 D1 的入口 |

**「单边出现」是最强的信号**：一个 `upsert` 改了而 `remove` 没改、`encode` 改了而 `decode` 没改、
Go 侧改了而 TS 侧没改。判据 D1 的检查法就是为这类场景准备的。

### 3. 三类必查（差分审查独有的关注点）

**(a) 漏改 — 同一次改动里的对称缺失**

- 改了一侧的实现，另一侧（同语言同功能 / 跨语言镜像 / 契约与生成物）是否同改
- `AGENTS.md` 的「同任务同步」义务清单：petal 声明、`docs/API*.md`、用户指南、i18n 全语言、
  `entryVisibility/catalog.ts`、快捷键文档
- 删除了某个成员/字段/常量后，是否还有引用

**(b) 改动引入的新问题**

- 新代码是否重犯了模式库里的已知模式（`patterns.md` 是清单，逐条对照比凭空想快）
- 新增的守卫/校验是否**在全部副作用之前**（判据 D1j、P30）
- 新增的配置字段是否会被静默丢弃（判据 D3c、P27）

**(c) 改动声明的与实际的不一致**

- 提交信息说「已修复 X」而 diff 没覆盖 X 的根因 —— 这是验证模式第 ① 条硬约束的差分版本
- 注释/文档说「保留行为」而 diff 显示行为变了（判据 D1n、P38 的修法陷阱）
- 声称「已加测试」而测试不在 CI 执行集内（判据 G4）

### 4. 爆炸半径（比全量审计更省力，因为 diff 已经限定了入口）

对每个被改动的**函数签名、导出符号、配置字段、契约字段**：

- 谁调用（grep + 语言服务；grep 会漏字符串引用、反射、路由注册、模板，见修复手册第 1 节）
- 谁消费这个值（写到磁盘 / 网络 / DOM / 用户屏幕）；**消费端可能读的是另一个字段**
- 跨端 / 跨设备 / 跨角色：同步、只读、发布、移动端、浏览器扩展

### 5. 过挑战门

判据与挑战门与审计模式完全相同（含「修复方案的挑战门」）。
**不要因为「只是个小改动」而跳过**——小 diff 的发现更容易被当成「作者故意的」。

### 6. 输出

用 `SKILL.md` 的主报告条目模板，但「位置」字段改为指 **diff 中的行**，
并在「证据」里给出 `git diff` 片段（行内代码，最多 3–5 行）。

## 常见误报（本模式特有）

| 形态 | 为什么不是缺陷 |
|---|---|
| 「改动没加测试」 | 若该仓库的既有惯例就是不补测试（`evidence.md` 实测只有 30% 的 bug 提交补了测试），这是**惯例差异**而非本次改动的缺陷。要报就报「测试缺口」这个独立项 |
| 「只改了一侧」但两侧本就不同源 | 先确认两侧**语义是否同一件事**。跨语言同名常量表差异方向可能相反（见「已知误报」）；`/// #if MOBILE` 编译期剔除会让某端本就没有对应实现 |
| 提交信息与 diff 不符 | 若 diff 本身自洽，这是**提交卫生问题**，严重度低；只有在「声称修复但根因未覆盖」时才升级 |
| 格式/重排造成的巨大 diff | 先 `git diff -w`（忽略空白）再看。纯重排不改变语义，但要确认**没有顺手改掉一处逻辑** |

## 与修复模式的衔接

差分审查中发现的问题，若用户随后要求修复：
- 改动本身就在 diff 里，**变体分析可以直接用 diff 的对称性做**
- 验证闭环从第 1 级开始走（见 [修复手册第 5 节](./repair-playbook.md)）
- 提交时注意：**不要把审查发现的修复与新改动混在同一个提交**，否则回归归因变难
